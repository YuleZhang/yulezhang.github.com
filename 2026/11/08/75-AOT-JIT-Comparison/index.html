1. 先用一句人话理解 JIT

JIT（Just-In-Time，即时编译）就是：不急着在软件发布前把所有代码都编好，而是等程序运行、拿到一部分真实信息后，再编出适合这次任务的代码。

代码最终需要变成处理器能够执行的指令。AOT 和 JIT 的核心区别首先是编译发生在什么时候，而不是谁一定更快：

AOT（提前编译）：软件发布前就编好，好比提前印好说明书，用户拿到就能照着执行。
JIT（即时编译）：运行到某段代码时才编译，好比遇到具体问题再现场翻译；既可能多花一次编译时间，也有机会利用已经知道的设备和输入条件做优化。

需要先纠正一个容易误会的地方：AOT 不等于通用低性能，JIT 也不等于自动最优。 AOT 完全可以事先编译许多精心调优的 kernel，运行时再挑一个；JIT 也可能只是在运行时编出一份普通代码。真正影响性能的，是编译器掌握了哪些信息、生成了什么代码，以及选择了什么执行策略。

想边读边试，可以直接运行文中配套的两个小实验：JIT 第一次为什么慢 和 GEMM 为什么要按 shape 选配置。只需 Python 就能跑通demo，不要求 NVIDIA GPU；第3节还提供了可选的 Triton/CUDA 版本。

M、N、K 可以取很多不同的整数；再考虑 FP32 / FP16 / BF16 / INT8 等数据类型、矩阵是否转置、内存布局、设备架构、tile 大小和线程配置，实际要适配的场景就会非常多。

2.1 完全可以先写一个通用 kernel

比如写一份通用 GEMM 逻辑：

M/N/K 是运行时参数；T 可以在源码层复用同一份算法逻辑。发布时，针对 float / half / bfloat16 等类型分别实例化或分发实现，便能覆盖大量 shape 和 dtype。同一份通用源码不一定意味着同一份机器码：不同 dtype 往往对应不同指令、累加精度和硬件路径。

一个通用 kernel 只要正确处理边界、stride 和数据类型，就能完成工作。对于不常见 shape、调用次数少的场景，它甚至可能是更划算的选择。

问题在于：“什么都能算”和“每种情况都算得快”不是一回事。

  • M/N/K 很小：kernel launch 和调度开销可能比计算本身还显著。
  • M/N/K 很大：更在意 Tensor Core/矩阵指令利用率、tile 复用、流水线与寄存器压力。
  • 矩阵很“瘦长”：最适合方阵的分块方式可能留下大量空闲线程或无效计算。
  • dtype、对齐、layout 不同：可能需要不同的向量化、load/store 或矩阵指令路径。
  • 如果让一套固定的 tile / warps / stages 应对所有情况，往往只能在一部分输入上接近最优。

2.2 JIT 的优势，是在“已知条件”上做针对性优化

假设服务启动后知道这次计算是：M=128、N=4096、K=4096、FP16、NVIDIA GPU。此时可以：

  • 特化：固定某些 tile、对齐或静态配置，让编译器展开循环、消除满足条件时不必要的分支，并使用合适的指令。
  • 选择算法：在不同 tile、线程组织、流水线深度之间做选择；这一步可以靠启发式，也可以靠 benchmark/autotune。
  • 缓存结果：下次遇到满足同样编译前提的请求，直接复用已经编好的产物。
    这里也不意味着必须把 M/N/K 的每个值都写死。实际系统经常采用少量特化变体 + 动态 shape + 运行时分发，覆盖一个 shape 家族，而不是每个输入生成独立机器码。

可以把几种策略放在一起看：

策略 怎么做 优势 代价
单一通用实现 一套 kernel 接受动态 shape，按 dtype 做必要分发 覆盖广、简单、无逐 shape 编译 某些 shape 下性能可能不理想
AOT 多变体 提前编好多个 tile / dtype / ISA 版本，运行时挑选 无在线编译成本，也能很快 二进制体积、预编译和维护成本更高
JIT 特化 运行时根据已知条件编译、缓存 变体更灵活，可针对设备和工作负载 首次编译、缓存管理和重编成本
混合方案 AOT 负责常用路径，JIT 或回退处理特殊路径 兼顾启动速度与覆盖率 整体工程复杂度更高

所以 JIT 真正解决的是：什么时候值得拿运行时已知的信息，换一份更优的代码

2.3 有公开的 GEMM 性能数据吗？

有！Trition官方的 Matrix Multiplication 教程 给了两个很直观的观察点。

观察一：同样是 GEMM，换一种分块调度就能更快。 官方教程提到，在 A100 上把 block 的执行顺序调整为更利于 L2 复用的 grouped ordering，在某些配置下吞吐量可由约 220 提升到 245 TFLOPS（约 +11%）。这不是因为 GEMM 数学公式变了，而是数据访问和 tile 调度更贴合硬件。它说明执行策略的选择确实有价值，但不能单凭这组数据证明 JIT 比 AOT 快——AOT 同样可以提前编译这套调度。

观察二：Triton 也不保证处处赢过 cuBLAS。 官方教程附带的一组 FP16 方阵 benchmark 示例数据如下（单位 TFLOPS）：

GEMM (M=N=K) cuBLAS Triton 观察
512 26.2 23.8 此样例中 cuBLAS 更快
1792 172.9 204.0 此样例中 Triton 更快

这些是官方教程展示的样例输出，并不是真机复测；性能受 GPU、版本、时钟、精度与 benchmark 方法影响。更重要的是：cuBLAS 本身就是高度优化、拥有大量实现和启发式选择的库，不能把它简单等同于“单一通用 kernel”，也不能把此表当作“JIT 对 AOT”的受控对照。

真正要验证“现场翻得更合身”，应该在同一 GPU、同一 dtype、同一组 shape、相同计时条件下，测 固定通用 tile、离线准备的多变体分发、JIT 特化/调优，再单独统计编译耗时和缓存命中率。

这就把第 2 节的论点落到了可观察的证据上：JIT 可以成为生成、特化或管理不同变体的手段，但性能收益来自选对实现，不来自「编译发生得晚」本身。

3. 来从一个 Triton kernel 角度看 JIT

Triton 很适合观察这条链路，因为一个短小的 Python kernel 就能触发编译、生成 GPU 机器码并执行。

这里最值得看的是 BLOCK: tl.constexpr：它是编译期常量。比如把 BLOCK=256 改成 BLOCK=128，对应的向量范围、程序布局等就可能变化，需要另一份编译变体。

但并不是所有参数都会按具体数值特化。例子里的 n 可以继续作为运行时长度，负责边界 mask；Triton 还会根据参数类型、对齐和显式特化策略决定哪些信息进入编译前提。triton.jit API 甚至提供 do_not_specialize，用于限制不必要的值特化。

第一次调用可能慢在多个环节：编译本身、模块加载、CUDA 上下文初始化、首次内存分配、autotune。所以“第一次慢”不可以全部归因于 JIT，做实验时要把这些成本分开。

还要区分三个术语：

  • Codegen（代码生成）：可以从 IR 生成另一种 IR、目标汇编，甚至直接生成机器码；不只等于“拼源码字符串”。
  • Lowering / Pass：对 IR 做变换和优化，是编译器内部的处理环节，本身不等于 JIT。
  • JIT：描述编译在运行期发生。它可以调用上述 codegen 与 pass，也可以在 CPU 上直接发射机器指令。

3.2 编译产物靠什么标识并缓存？

一个编译产物需要能回答：“这次请求，是否还能安全复用上次的机器码？”

以 Triton 为例，影响编译变体的因素一般包括：kernel 源码/定义、参数类型及参与特化的属性、constexpr、num_warps / num_stages 等编译配置、目标后端与设备能力，以及相关编译环境版本。

不要简单理解成“M/N/K 和所有运行时变量都必须进 key”。只有生成代码确实依赖的条件，才需要成为特化依据或有效性检查的一部分；否则新 shape 也可能安全复用同一个动态 kernel。

这里存在三种不同的“键”或判断：

概念 解决什么问题 示例
编译缓存 key 这份编译产物能否复用？ BLOCK、dtype、目标架构、编译选项
Guard / 有效性条件 这次输入是否满足已编译代码的假设？ shape 区间、stride、dtype、模型状态
Autotune key 哪些输入条件需要重新选择更快的候选？ 某个 M/N/K 家族、布局或精度

key 过细，会反复编译、缓存膨胀；key 过粗或 Guard 不完整，可能执行不适用的代码，带来错误结果甚至内存安全问题。

3.3 特化和调优是一回事吗？

不是。继续拿 GEMM 来看：

特化（specialization）：根据已知信息，决定这份代码长什么样，比如 tile 大小、常量折叠、循环展开。
调优（autotuning）：在多个正确候选里进行测量或选择，决定这一类输入用哪份代码。
JIT 不必依赖 autotune，autotune 也不要求在线 JIT：提前编好的几个 AOT kernel 一样可以在运行时测速、选择并缓存结果。

4. JIT 到底可以发生在哪些地方？

JIT 不只用于一个 kernel。按优化对象看，可以从计算图一路下沉到机器指令；但下面这些是不同的编译/优化层次，不是每一项都属于 JIT。

层次 主要解决什么 典型项目/机制
图 / 区域级 跨算子融合、消除中间张量、选择算子边界 torch.compile / Inductor、XLA、TVM Relax
算子 / kernel 级 针对 shape、dtype、layout 和设备生成或选择实现 Triton、oneDNN、VkFFT；CUTLASS 模板实例
调度级 分块、线程映射、内存层次、流水线如何组织 Halide schedule、TVM TIR schedule
指令 / ISA 级 利用 AVX/AMX/NEON 或特定 GPU ISA oneDNN JIT、Xbyak/AsmJit、编译器后端
调优 / 选择层（伴随） 在合法候选中寻找更优配置 Triton autotune、TVM autotuning、cuBLASLt heuristics
IR / Pass 层（内部机制） 规范化、融合、lowering、指令选择 MLIR、LLVM 的 pass pipeline

4.1 再看一个不同的例子：VkFFT

VkFFT 支持多种 GPU API，会在运行时根据 FFT 长度、维度、精度、设备约束等做计划并编译 kernel。不同长度可能走不同 radix 分解；某些质数长度会使用 Rader 或 Bluestein 等算法。

这仍然不是“连续变体空间”：FFT 长度是离散整数，实际还受设备内存和实现上限约束。真正难的是有效组合数量很大，而且不同组合的最佳算法和内存调度可能明显不同，不适合把所有排列组合都提前编成二进制。

VkFFT 能清晰展示另一种 JIT 形态：运行时做算法规划 → 生成针对该计划的代码 → 交给后端编译器 → 执行。它和 Triton 的区别主要在表达形式与规划逻辑，而不是“一个是离散、一个是连续”。

4.2 有三个概念，最好别混用

  • JIT ≠ Fusion（融合）：JIT 说的是编译时机；融合说的是如何减少算子边界和中间数据搬运。AOT 也能融合。
  • JIT ≠ Autotune（自动调优）：JIT 决定何时编译；autotune 决定如何选择。两者可以配合，也可以独立存在。
  • JIT ≠ GPU 专属能力：CPU 上也有 JVM、oneDNN、Xbyak/AsmJit 等 JIT。移动设备可能受代码签名、W^X 和动态执行权限限制；在手机或封闭设备上，JIT 未必是实际可部署的最优方案。

5. 图级 JIT 是怎么工作的？看看 PyTorch

如果一个网络要跑 matmul → add bias → activation，只加速其中一个 GEMM 还不够：中间张量的读写和多次 kernel launch 也会耗时。

torch.compile 就是在更大的计算图上寻找这些机会。典型路径可以概括为：

  • 图级优化：决定哪些操作融合、哪些中间结果不必写回显存。
  • kernel 级优化：将融合后的工作交给 Triton、C++ 或其他合适的后端实现。
  • Guard：判断新输入是否仍满足已捕获图的假设，不满足时可能重新编译或走回退路径。
    例如 batch size 从 8 变到 16，并不天然意味着必须重新生成所有 kernel。PyTorch 支持 dynamic shapes，允许某些维度在一个编译产物里保持动态；代价是放弃对应维度的一部分静态优化机会。

它与第 3 节的 Triton cache key 是相关但不同层级的问题：前者保障图级假设，后者保障具体 kernel 编译变体的复用。

6. 图级和 kernel 级一定都要上吗？

不一定。要看瓶颈。

  • 如果瓶颈是大量碎 elementwise op、频繁 launch 和中间 tensor 访存，图级融合往往很有价值。
  • 如果瓶颈是一颗 GEMM 或 attention kernel 的 tile 组织、矩阵指令利用率，kernel 级调优更直接。
  • 如果算子已经由高度优化的 cuBLAS/cuDNN/专用 attention kernel 实现，强行全部改成 JIT 可能增加复杂度却没有收益。
  • 如果是一次性离线任务、短生命周期进程或受限端侧部署，编译成本可能根本摊不回来。
    两级可以协同，也可以只做一层。先找到瓶颈，再选择编译粒度；不要为了上 JIT 而上 JIT。

7. 常见框架擅长什么，该怎么选？

框架 / 库 主要强项 适用场景 要注意的边界
PyTorch torch.compile 捕获模型图、融合、接入 Inductor/Triton 已在 PyTorch 中开发训练或推理模型 Graph break、Guard、重编译和冷启动
XLA / JAX 以编译式图优化组织计算，支持 TPU 等后端 JAX/TPU 或端到端计算图优化 整图编译成本与动态形状约束
TVM（Relax/TIR） 图/算子联合优化、可编程调度、跨设备编译 多硬件部署、自定义调度 端到端工程集成与搜索成本
Triton 用 Python 风格 DSL 编写并 JIT 编译 GPU kernel 自定义 GEMM、融合算子、attention 不是完整模型图编译器
Halide 算法与 schedule 分离 图像处理、规则流水线 不应简单等同于 GPU 在线 JIT
oneDNN 高性能 primitive、ISA 专用优化及缓存 CPU 密集型推理、基础算子 部分路径 JIT，其他路径为预编译实现
CUTLASS GEMM/Conv 模板与 epilogue 定制 高性能 NVIDIA GPU 算子开发 传统模板实例化主要是 AOT，不等同 JIT

oneDNN 展示了 CPU 侧运行时代码生成的价值；CUTLASS 则展示了即使不用在线 JIT，也可以利用模板、多变体与调优获得高性能。把两者放在一起，反而更容易理解“JIT 只是手段，不是性能保证”。

8. AI 编译器为什么会用到 JIT？

AI 编译器要做的事情，往往不只是把一段代码翻成机器指令，而是把模型运算映射到特定硬件、特定输入和特定执行计划。

以一个 LayerNorm → Linear → GELU 子图为例：

这里既可以完全离线 AOT，也可以在运行期引入 JIT。后者通常适合下面几类情况：

场景 运行时多知道了什么 JIT 可能带来什么
动态 shape 当前 batch、sequence length、图像尺寸 特化一部分维度，减少无效工作
动态 dtype / 量化配置 FP16/BF16/INT8、量化 group size、scale layout 使用更匹配的数据路径或融合反量化
已知目标硬件 实际 ISA、SM 架构、共享内存和寄存器约束 选择更合适的 tile、流水线和指令
算子融合 当前计算图中的相邻操作 将 bias、激活、转换等融合进 kernel
多种执行形态 输入分布、并发模式、算子参数 按性能模型或 autotune 选择候选

不过，图优化发生在运行时，不代表最终机器码一定由 JIT 生成：编译器也可能只在运行时选择一颗已经 AOT 编好的 kernel。判断一个系统是不是 JIT，要看它是否真的在运行期间生成/编译了新的可执行代码，而不能仅凭“运行时做了优化”就下结论。

9. 大模型开发中，JIT 到底扮演什么角色？

大模型训练和推理非常依赖 GEMM、attention、归一化、激活与量化。JIT 在这里的价值，主要不是改变 Transformer 公式，而是减少执行这些公式的开销。

9.1 训练：把反复执行的子图编得更高效

典型场景是 PyTorch 训练用 torch.compile 优化前向/反向图，融合一些短小的 elementwise 操作、改进内存访问和 kernel 调度。长 Transformer 中相似的 block 反复出现，也可以考虑区域编译、复用编译结果，降低冷启动成本。

PyTorch 的 regional compilation 教程 就是针对“模型大、首次编译慢”这个真实问题。

9.2 推理：Prefill 和 Decode，需要的优化经常不同

阶段 计算形态 主要优化关注点 JIT 能做什么
Prefill 一次处理较长 prompt，GEMM/attention 计算密集 大矩阵吞吐、融合、attention 为常见 shape 或 token 范围选择更合适的算子配置
Decode 每步生成少量 token，KV cache 参与注意力计算 launch 开销、访存、batch 变化、低延迟 特化适用的 kernel、融合小算子、减少低效访存
量化推理 INT8/INT4 等权重与 scale/zero-point 解码 反量化开销、矩阵指令、layout 将解码和 GEMM 等操作融合或选择专用路径

要注意：PagedAttention、continuous batching、KV cache、CUDA Graph 都不等于 JIT。 它们分别解决存储/调度/执行复用的问题，可以和 JIT 一起使用，也可以与 AOT kernel 配合。

9.3 一个真实例子：vLLM 为什么会接入 torch.compile？

vLLM 的编译配置文档 描述了从直接 eager 执行、标准 torch.compile，到 vLLM 自定义编译后端的不同模式。自定义后端涉及图分段、缓存、shape specialization 和 Inductor pass；其 CUDA Graph 设计 则负责捕获与重放执行。

把它们拆开看，会更容易理解整套推理系统：

关键不是“每生成一个 token 都重新 JIT”，而是尽量让绝大多数请求落在已经编好、预热好、能复用的路径上。真实 serving 系统会努力避免 token 长度或 batch 每变化一次，就引发昂贵的整图重编译。

9.4 什么时候反而应该优先选 AOT？

部署到移动设备、NPU 或严格控制启动延迟的在线服务时，经常更适合提前编译 + 少量变体 + 运行时分发。例如，固定模型/设备、已知 batch 范围的场景，把编译成本挪到构建和发布阶段，可能比把完整编译器打包进终端更合适。

PyTorch 也提供 torch.compile 的 AOT 编译与产物序列化路径。这进一步说明：图级优化、Triton 代码生成和 autotune，并不天生要求发生在用户第一次请求时。

10. JIT 什么时候真的划算？算一笔账

假设某个 AOT 通用实现每次执行需要 T_generic，特化实现每次需要 T_specialized，首次编译需要 T_compile，之后复用 H 次。

简化估算：

只有当 T_generic > T_specialized 且 H > T_compile / (T_generic - T_specialized) 时，JIT 的累计时间才可能更划算。

例如：编译花 2 秒、每次快 0.2 毫秒，要复用超过 10,000 次才能回本（尚未计入 autotune、额外内存、缓存 I/O 和服务冷启动）。对高频模型服务可能值得；对偶尔触发一次的算子，就未必。

这个公式是理解成本的简化模型。在真实部署中，还要考虑 AOT 多变体的性能、缓存跨进程持久化、设备升级、代码体积、编译器版本、并发编译，以及 P50/P99 延迟。

11. 真要在工程里使用 JIT，先检查什么？

  • 基准要分开测：分别记录冷启动/首次编译、缓存命中后的 steady-state、autotune 耗时和端到端延迟，避免把初始化混入 JIT 结论。
  • 先识别特化维度：shape、stride、dtype、layout、设备架构、静态配置；哪些必须固定，哪些应保留动态？
  • Guard 要守住正确性：每个产物都要有清晰的适用条件，失效时能够重新编译或安全回退。
  • 缓存要可解释：知道 key 的组成、编译器/驱动升级后的失效条件、存储位置、容量上限和淘汰策略。分层缓存可以存在，但边界要清楚。
  • 预热要针对真实流量：从热点 shape 开始，不要漫无目的地穷举所有变体。
  • 要有非 JIT 回退路径：图抓取失败、编译失败、硬件不支持或冷启动预算不足时，仍能保证功能正确。
  • 先保证数值和内存安全：验证不同 dtype 的累加精度、shape 边界、别名、stride、并发与设备行为，再看 GFLOPS。
  • 最后才判断收益：对比真实瓶颈、编译摊销和全链路吞吐，别只比较单颗 kernel 的峰值。

12. 常见疑问，快速对照

问题 简短回答
只要 shape 多，就一定要用 JIT？ 不一定。动态 shape 的通用 kernel、AOT 多变体和 runtime dispatch 都能覆盖大量输入。
一份通用 kernel 能处理不同 dtype 吗？ 算法逻辑可以共用；最终通常仍需类型实例化、分发或其他类型处理机制。
JIT 就一定比手写 CUDA / cuBLAS 快吗？ 不一定。看是否有更好的特化、融合、调度和实测表现。
Codegen 就是 JIT 吗？ 不是。Codegen 是生成代码的步骤；JIT 指运行时编译的策略。
Pass、Fusion 和 JIT 是一回事吗？ 不是。Pass 是编译器变换，Fusion 是优化方法，JIT 是编译发生的时机。
同一个 shape 就肯定命中缓存？ 不一定。dtype、stride、静态参数、目标设备或编译版本变化也可能影响复用。
大模型每生成一个 token 都要 JIT 吗？ 不应该如此。线上系统的目标是让常见请求命中预编译或缓存变体。
CUDA Graph 和 JIT 有什么区别？ 前者捕获并重放 GPU 执行序列；后者生成/编译代码。能协作，但不是一回事。
部署端不能 JIT，是否就做不了融合？ 仍能在离线编译阶段融合、特化并发布 AOT 产物。

把文章和代码连起来

文章里的三个问题，现在都能在源码中找到对应观察点：

想验证什么？ 从哪里开始？ 观察结果时注意什么？
第一次调用为什么慢、缓存是否复用？ JIT first-call Demo · python run.py 首调用总时间不等于纯编译时间；再次运行进程还可能命中磁盘缓存
数组长度变化一定要重新编译吗？ 同一个 Demo 的编译签名统计 这份 Numba 示例中，长度变化不新增签名，dtype 变化会新增签名

ExecuTorch 的设计理念：把模型变成端侧程序

2026-11-22
技术
Word count: 6.7k   |   Reading time≈ 25 min

设想手里有一个已经训好的 PyTorch 模型。现在要把它放到手机上，并让其中一部分跑在 Qualcomm HTP 上。

第一反应很容易是：找一个 converter，把 PyTorch 模型转成 QNN Binary，不就结束了吗？

真正动手时，问题很快就冒出来了。模型里的参数和动态 Shape 怎么带走？量化是谁决定的？遇到 QNN 不支持的算子怎么办？后端编译产物由谁加载？设备上的中间 Tensor 放在哪里？为了几个算子，难道要把整套 Kernel 都编进 App？

这些问题不属于同一层，也不该塞进同一个 converter。ExecuTorch 的设计价值，恰恰在于把它们拆开：通用层负责把模型整理成一份端侧程序，Backend 只接管自己擅长的子图，设备上的 C++ Runtime 再把两边接起来。

QNN 在这里是一个很合适的观察窗口。沿着这条链路走一遍，ExecuTorch 为什么要有这么多层，就不再抽象了。

先跟着模型走一遍

从构建机到手机，模型会经历三段不同的旅程：

第一段是 Program Preparation：把 Python 世界里的模型变成一份完整程序。第二段是 Runtime Preparation：为目标平台准备真正需要的 Runtime、Kernel 和 Backend Library。第三段才是 Program Execution：设备加载 .pte，按里面的指令执行普通算子或调用 Delegate。

这三段一旦混在一起，很多概念就会串位。比如 Partitioner 决定“哪些节点交给 QNN”，Selective Build 决定“最终二进制里要编进哪些 ExecuTorch Kernel”。它们都像是在“做选择”，选的却不是同一种东西。

ExecuTorch 的总体取向也藏在这张图里：能在设备执行前确定的事情，尽量提前确定。图变换、后端编译、Tensor 生命周期分析都放到 AOT 阶段，设备端留下一个相对轻量的 C++ Runtime。

这不等于运行时从此没有动态行为。控制流和动态 Shape 仍然存在，只是执行结构、内存边界和后端分工会尽可能提前明确。

这里同时出现了 ATen 和 FX，很容易让人以为它们是一回事。其实 ATen 回答“这个算子是什么”，FX 回答“这些算子怎样连成图”。

  • ATen 是 PyTorch 的 Tensor 与 Operator 体系。aten.convolution.default 描述卷积的语义和参数契约，并不等于某个 CPU Kernel。
  • FX 提供 Graph、Node、GraphModule 这些图结构。所谓 ATen FX Graph，只是说 FX 节点的 target 是 ATen Operator。

但后端只拿到 x → convolution → relu 仍然没法工作。weight 在哪里？哪些输入来自用户？哪些是参数或常量？动态维度允许落在哪个范围？

这一层的意义不是“把 Python 函数画成图”这么简单，而是把后续编译需要的程序状态一起冻结下来。Backend 面对的是一份可分析的程序，而不是一张失去上下文的算子连线图。

为什么还要经过 Core ATen 和 Edge Dialect

有了 ATen Graph，为什么不直接翻译成 QNN Graph？

因为 PyTorch 的高层算子很多，而且不同写法可能表达相近的计算。如果每个 Backend 都直接面对完整的 ATen 世界，它们就要各自处理同一批模型捕获、算子拆解和语义归一问题。

Core ATen 先通过 decomposition，把高层复合算子整理到更小、更稳定的基础算子集合。这样做能减少后端需要理解的算子种类，也让通用图优化有更统一的输入。

不过 decomposition 不是拆得越碎越好。假如目标 Backend 原生支持 Conv2D，把卷积继续拆成更低层的计算，反而可能破坏算子映射和融合机会。哪些算子保留、哪些算子分解，必须考虑目标 Backend 的能力。

Edge Dialect 接着补上端侧执行真正关心的契约，例如 dtype、dim_order、Scalar 到 Tensor 的处理，以及 Custom Operator 的边界。它仍然是 ExecuTorch 的通用表示，不是 QNN IR，也不是把 ATen Operator 换了个名字。

可以把两层的分工记成一句话：Core ATen 收敛“有哪些计算”，Edge Dialect明确“这些计算以什么端侧契约存在”。到这里，QNN、Core ML、XNNPACK 等 Backend 才从同一个相对稳定的入口各自往下走。

量化为什么要先写进图里

量化最怕出现一种情况：前端认为 Tensor A 用一套 scale / zero point，后端却按另一套 encoding 执行。数值语义如果只藏在 converter 的参数里，图本身就很难检查这种错位。

Quantizer 是策略层。它表达硬件允许哪些量化配置、哪些边界可以量化，不是简单地把所有 Tensor 强制变成 INT8。Prepare 阶段插入 Observer 或 FakeQuant，Convert 再把收集到的量化语义落成明确的图节点。

图里出现 Q / DQ，也不代表设备上一定逐节点执行 Quantize 和 Dequantize。Backend 可以把它们融合进算子、转成 Tensor Encoding，或者在 encoding 不一致的地方插入 Requantize。重要的是数值转换仍然正确，而不是表面上删掉了多少 Q / DQ 节点。

一段子图交给 QNN，究竟经过谁

到了后端边界，最容易混淆的是 Partitioner、Backend 和 Delegate。沿时间顺序看，它们其实分别站在三处：

角色 发生在哪里 只回答一个问题
Partitioner AOT 图处理 哪些节点可以组成 Backend 支持的连续子图？
Backend AOT 编译 怎样把这段子图编译成 Backend 产物？
Delegate 设备 Runtime 怎样加载并执行这个产物？

Partitioner 会检查 operator、dtype、Shape 和其他约束。支持的节点被标成 QNN partition，不支持的节点继续留给 ExecuTorch Runtime 或其他 Backend。它负责划边界，不负责编译 QNN Binary。

随后 QNN Backend 的 preprocess 接收分区后的 Edge Program 和 CompileSpec。图结构相同，目标 SoC、精度或图配置不同，编译结果也可能不同。这个阶段才会完成 QNN 算子映射、图构建、Finalize 或 Context 编译，并返回 compiled blob。

到了设备端，Delegate 接过这份 blob。ExecuTorch 用统一的 init()、execute()、destroy() 生命周期接入它；真正执行图的仍然是 QNN Runtime。Delegate 是通用 Runtime 与具体后端之间的插座，不是 QNN Runtime 的替代品。

这个拆分还带来一个很实际的能力：Partial Delegation。真实模型里总会有某些算子、Shape 或数据类型不被同一个 NPU 支持。ExecuTorch 不要求整个模型一次性下沉，而是允许 QNN 子图和普通 Runtime 算子出现在同一份程序里。

QNN Context Binary 和 .pte 为什么不能画等号

Backend 编译结束后，会同时看到两种很像“模型文件”的东西：QNN Context Binary 和 ExecuTorch Program。它们描述的范围不同。

QNN Context Binary 只覆盖交给 QNN 的分区。.pte 则要描述完整的 ExecuTorch 程序：普通算子怎么执行，Delegate 在哪里被调用，常量和元数据如何组织，Tensor Buffer 如何安排。

所以 .pte 不是另一种 QNN Context Binary，更接近一份异构执行计划的封装。QNN blob 是其中的一个 payload。

内存规划和 Selective Build，省的不是同一种资源

模型已经能执行了，ExecuTorch 还要处理两个端侧很现实的问题：运行时内存和二进制体积。

AOT Memory Planning 关心 Tensor Buffer。它先传播 TensorSpec 和符号 Shape，再估计动态维度的边界，最后分析每个 Tensor 从何时存活到何时。如果两个 Tensor 的生命周期不重叠，它们就有机会复用同一段 arena：

这里规划的是 ExecuTorch 程序看到的 Tensor Buffer。Delegate 内部申请的 Context、工作区或后端资源仍由 Backend 自己管理。把两者混成一个内存池，会让问题定位从一开始就走偏。

Selective Build 关心的则是代码。构建系统从 .pte、operator list 或 YAML 中提取真正需要的 operator 和 dtype variant，只把对应的 Portable / Optimized Kernel 注册进目标 Runtime。QNN Delegate 和 QNN Runtime 通常独立构建、独立链接，不会因为 ExecuTorch Kernel 被裁剪就自动变小。

因此，这两项优化虽然都发生在 AOT / build-time，账本完全不同：Memory Planning 减少运行时 Buffer 压力，Selective Build 减少随应用交付的 Kernel 代码。

这些层不是为了把系统画复杂

回到开头那个“找个 converter”的直觉。它的问题不在于转换不存在，而在于把太多职责压成了一个词。

模型捕获需要保存程序状态；通用 IR 要给不同 Backend 一个稳定入口；量化要保住数值语义；Partitioner 要允许部分下沉；Backend 要针对硬件编译；Delegate 要接入设备 Runtime；内存规划和 Kernel 裁剪又分别处理 RAM 与包体积。

把这些责任拆开之后，前端和后端可以独立演进。QNN Backend 不必重新发明 PyTorch 模型捕获，ExecuTorch Runtime 也不必理解 QNN Graph 里的每个节点。设备执行时，它只需要知道下一条是普通 Operator，还是一次 Delegate 调用。

代价当然存在：层次更多，调试时必须先判断问题落在哪个边界。量化误差要看图里的 encoding 传递，未下沉算子要查 Partitioner 的支持条件，QNN 执行失败要分清 blob 编译和 Delegate 生命周期，内存问题也要先区分 ExecuTorch arena 与 Backend 内部资源。

但这正是分层带来的另一面：只要边界清楚，复杂问题就能被切成可定位、可替换的局部问题。ExecuTorch 做的不是把一个 PyTorch 模型“换一种格式”，而是把它整理成一份能在端侧被构建、裁剪、加载并异构执行的程序。

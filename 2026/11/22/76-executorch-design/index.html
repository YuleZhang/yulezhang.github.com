ExecuTorch 的设计理念：把模型变成端侧程序

2026-11-22
技术
Word count: 11.3k   |   Reading time≈ 42 min

公开版：只使用 ExecuTorch / PyTorch / QNN 等公共项目作为锚点，可独立阅读、可对外分享。 带完整分层细节的个人消化版见 通过QNN了解execuTorch的设计理念。

1. 一句话版本

ExecuTorch 不是"把 PyTorch 模型转成硬件 Binary"的 Converter，而是一套端侧模型准备、编译、打包和执行体系。

一个 PyTorch 模型要跑到手机上，中间要回答一串彼此独立的问题：怎么把模型完整抓下来、算子怎么规范化、量化策略放哪、哪些图交给 NPU、后端产物长什么样、内存什么时候规划、Runtime 里到底要编哪些 Kernel。

ExecuTorch 的做法是给每个问题一个独立的层，并且尽量把它们全部推到设备执行之前。QNN 只是这套体系里的一个 Backend。

2. 三个阶段，别混成一件事

三个阶段各自只回答自己的问题：

阶段回答什么产物
Program Preparation模型怎么变成一份完整程序.pte（内含 Delegate Blob）
Runtime Preparation目标平台上到底要哪些代码裁剪后的 Runtime + Kernel Library
Program Execution设备上怎么把它跑起来普通 Kernel 与 Delegate 的混合执行

这里最重要的设计原则是：尽可能把工作前移到 AOT，保留一个轻量、可移植的 C++ Runtime。

设备端不需要重新运行 Python 模型定义，也不需要每次推理都重新分析整张图、重新做后端编译、重新规划 Tensor 生命周期。

但别把 AOT 理解成"运行时完全没有动态行为"——ExecuTorch 仍然支持控制流和动态 Shape。区别在于它会尽量提前明确执行结构、内存需求的边界以及后端分工。

3. 前端：先把"算子"和"图"分开

这三个概念最容易被混为一谈，因为它们处在不同层次：

FXPython 图表示Graph、Node、GraphModule

两个容易错的点：

  • ATen Operator 不等于 CPU Kernel。 它表达算子语义；最终可以由 CPU Kernel 执行，也可以被编译成 QNN、CUDA 等后端算子。ATen 是统一的算子语义入口，不是已经定好实现地址的 Dispatch 表。
  • "ATen FX Graph" 指的是一张用 ATen Operator 作为 Node Target 的 FX Graph，不是两种东西的合体。

而 torch.export.export() 返回的 ExportedProgram 远不只是 GraphModule：

只知道 x → convolution → output 不够。编译器还必须知道 weight 在哪、哪些输入是用户输入、常量如何保存、Shape 是固定还是动态。所以后端编译器通常不应该只拿到一张孤立的 Graph 就开始编译。

4. 规范化：Core ATen 与 Edge Dialect 是两件事

拿到 ATen Graph 之后为什么不直接转成 QNN Graph？因为 ATen Operator 数量庞大、含很多高层复合算子，Operator Set 越大，后端要支持、优化和实现 Kernel 的复杂度越高。

于是有两次各自目的不同的规范化：

第一次，Core ATen：缩小并规范化算子集合。 把高层算子按 decomposition 拆成更基础的算子：

它减少需要处理的算子种类、让通用图优化可以针对基础算子开展、让不同 Backend 复用同一套规范化语义。但decomposition 不是越彻底越好——QNN 原生支持 Conv2D 时，把 Conv2D 拆成低层算子反而可能破坏原生算子映射和融合机会。所以要根据目标 Backend 的能力决定保留还是分解。

第二次，Edge Dialect：明确端侧部署契约。 它规定 Operator 必须带 dtype 与内存布局信息（dim_order）或是已注册的 Custom Operator、Scalar 要转换成 Tensor，并且这些信息还能给 Selective Build 当依据。

Edge Dialect 不是 QNN IR，也不是给 ATen Operator 改个名。 它是 ExecuTorch 为端侧编译定义的标准化表示。

这样分层的关键收益是：通用前端负责标准化图，具体硬件后端不必各自重新实现模型捕获和所有通用图语义。

5. 量化：让量化语义成为 Graph 的一部分

ExecuTorch 的量化生态使用 torchao，多数 Backend 走 PT2E 流程。但每个 Backend 可以定义自己的 Quantizer——硬件支持的量化配置本来就不一样。

PTQ 和 QAT 的共同点在于都由 Backend-specific Quantizer 提供策略，分歧在准备阶段和数据流：

三步各自的职责：

  • Quantizer：定义哪些 Operator / Tensor 要量化、激活与权重的 dtype、Per-tensor 还是 Per-channel、Static / Dynamic / Weight-only、PTQ 还是 QAT。它是把硬件量化能力和模型图连起来的策略层，不是一个"把所有 Tensor 转成 INT8"的函数。
  • Prepare：按 annotation 规则找到量化边界，插入 Observer（PTQ）或 FakeQuant（QAT）。Observer 在 Calibration 阶段收集分布以确定量化参数；FakeQuant 在训练中模拟量化误差。
  • Convert：把 Observer / FakeQuant 变成图里明确的 Quantize / Dequantize 节点，于是量化语义可以被检查、评估，也能被后端识别和进一步优化。

不要把 Q/DQ 图理解成设备上一定逐节点执行 Quantize 和 Dequantize。 后端可以把量化参数映射到 Tensor Encoding、融合进 Operator，或在必要位置插入 Requantize、保留 Float Island。

对 QNN 来说，Backend 最终必须正确维护 Tensor 的 dtype、scale、zero point、axis 和 encoding。相邻算子输入输出 encoding 不一致时必须保证转换语义正确，不能为了删掉 Q/DQ 而破坏数值含义。

6. 后端链路：Partitioner、Backend、Delegate 必须分开

这是 ExecuTorch 后端体系最重要的抽象，三个角色在一条 AOT → Runtime 链路上各管一段：

  • Partitioner 只负责选图。 它回答：这个 Operator 受支持吗？dtype / Shape / 参数满足要求吗？能和前后节点组成连续子图吗？哪些必须留在 Runtime 或其他 Backend？它不生成 QNN Binary。
  • Backend 负责编译。 partition 标记并形成分区，preprocess 接收 Edge Program 子图和 CompileSpec，返回编译后的 Binary Blob。QNN Backend 内部会做算子映射、Tensor / Op 配置、图构建、Finalize / Context 编译。CompileSpec 是独立的编译控制面，用来传 SoC、后端类型、精度、图配置——同一份图在不同 CompileSpec 下可以产出面向不同目标的产物。
  • Delegate 负责运行时接入。 它提供 is_available() / init() / execute() / destroy() 四个接口。Delegate 不是 QNN Runtime 的替代品，而是 ExecuTorch Runtime 对具体 Backend 的统一接入层。

一个模型可以产生多个 Delegate partition，也可以保留未下沉的普通算子——这就是 Partial Delegation，它让异构执行成为可能：真实模型不可能保证每个 Operator 都被同一颗 NPU 支持。

7. 两种产物，别当成一个东西

产物作用范围主要内容
QNN Context BinaryQNN Backend 分区QNN 可加载的图编译产物
ExecuTorch Program（.pte）完整模型程序Runtime 指令、常量、内存规划、Delegate Blob 等

Backend preprocess 返回的编译产物会作为 Delegate Blob 被序列化进 .pte。所以：QNN Context Binary 描述 QNN 分区，.pte 描述完整的 ExecuTorch 程序。 一个 .pte 可以有多个 Delegate，也可以保留普通 Operator；设备端由 ExecuTorch Runtime 解析程序，遇到 Delegate 指令时调用相应 Backend。

.pte 是异构执行计划的封装，不是另一个 QNN Context Binary。

8. AOT Memory Planning：在编译期决定 Tensor 住哪

端侧频繁动态分配会带来性能、功耗和碎片问题。ExecuTorch 因此在 AOT 阶段尽可能确定 Tensor 的内存需求和生命周期，把它们安排进固定大小的 Memory Arena。

核心思想只有一句：

如果两个 Tensor 的生命周期不重叠，它们就可以复用同一段物理存储。

9. Selective Build：Runtime 不需要包含所有 Kernel

它解决的是一个完全不同的问题——最终要编进 Runtime 的 Kernel 实现有哪些：

四个要点：

  1. 它发生在 build-time，不是运行时动态裁剪；
  2. 裁剪的主要是 ExecuTorch 的 Portable / Optimized Kernel Library；
  3. Delegate Backend 通常独立构建和链接，不由 Kernel Selective Build 自动裁剪；
  4. Dtype Selective Build 能进一步减少无用的 dtype variant，但支持范围受当前版本和 Kernel Library 限制。

Selective Build 和 Partitioner 优化的不是同一种资源：前者裁的是"代码里有哪些 Kernel 实现"，后者决定"哪些图节点交给哪个 Backend"。

10. 为什么 ExecuTorch 要这样设计

不是单纯为了多加几层抽象。把前面合起来看，有四条真实的收益：

  • 前端与后端解耦：没有统一导出与 IR 层时，每个 Backend 都要重复处理模型捕获、算子语义、参数、Shape、量化。ExecuTorch 把通用能力放在前端和公共 IR 层，让 Backend 只聚焦硬件相关的图变换和编译。
  • Partial Delegation 让异构执行成为可能：Partitioner 把适合硬件的连续子图下沉，其余节点留给 Runtime 或其他 Backend，比"整个模型必须由单一硬件执行"灵活得多。
  • AOT 把成本从每次推理前移到离线：图变换、后端编译、内存规划、Kernel 选择都尽量在 AOT 完成，设备端只保留程序解释、Kernel Dispatch、Delegate 调用和后端执行。
  • Runtime 保持轻量，Backend 独立演进：Runtime 不需要理解 QNN Graph 的每个内部节点，只需知道这条指令是普通 Operator 还是 Delegate。QNN Backend 可以独立演进自己的 Builder、图编译和 Runtime 适配，硬件细节不会泄漏进通用 Runtime。

层次关键对象核心问题

最值得记住的五个结论：

  1. ATen 是算子体系，FX 是图结构，ExportedProgram 是完整导出程序。
  2. Core ATen 和 Edge Dialect 是不同阶段的规范化表示；Edge Dialect 不是具体硬件 IR。
  3. Partitioner 负责选图，Backend 负责编译，Delegate 负责运行时接入。
  4. QNN Context Binary 是后端产物，.pte 是完整 ExecuTorch Program。
  5. AOT Memory Planning 解决 Tensor Buffer 的生命周期与复用，Selective Build 解决 Kernel Library 的裁剪，两者优化的不是同一种资源。
